# 版本窗口与分支滞后

## 1. 公告里的三个时间概念

华为消费者月度公告只给三样与时间有关的信息，必须分开理解：

| 字段 | 含义 | 误用 |
|------|------|------|
| 页面 `更新时间` | 该月页面最后一次被编辑 | 当成「漏洞修复时间」 |
| `受影响版本` | 厂商认定的缺陷存在区间 | 当成「所有低于该版本的都受影响」 |
| CVE 发布/保留状态 | NVD 等外部库的元数据 | 当成「修复已发布」 |

**公告不给修复版本号**。它只说「这些版本受影响」，不告诉你「升到哪个版本修好」。

因此**不要**写「升级到 X 版本即可修复」——除非有独立证据（厂商补丁说明、上游公告、实际验证）。

## 2. 受影响版本 → 版本窗口

### 2.1 解析

`受影响版本` 形如 `HarmonyOS7.0.0，HarmonyOS6.1.0`，按 `，` 切分。

需要区分两类产品线：

- `HarmonyOS*`：手机/平板主线；
- `EMUI *`：旧产品线，仍会并列出现在同一行。

### 2.2 窗口的表达

不要把「受影响版本」当成 `<` 的数值比较。正确写法是**集合**：

- `affected`：公告列出的版本集合；
- `not_affected_stated`：公告未声明——**不等于**不受影响。

理由：

- 公告是**枚举**，不是范围；
- 未列出的版本可能「未评估」而不是「已修复」；
- 跨大版本（如 4.x → 7.x）没有可比的大小关系。

### 2.3 窗口的用途

窗口只回答一件事：**某个缺陷模式在哪些版本上应该存在**。它用于：

- 选择验证用的设备/镜像版本；
- 判断某分支是否落在窗口内；
- 排除「已在窗口外却仍报」的错误。

## 3. 分支滞后检测

### 3.1 前提

只有当修复落在**某条维护分支**、而目标分支仍在维护时，才做这一步。

典型形态：

- 修复 PR 的 base 是 `OpenHarmony-5.0.3-Release`；
- 同一缺陷在 `OpenHarmony-6.0-Release` 或 `master` 上是否也已修复，需要单独确认。

### 3.2 方法

1. 从修复 diff 里提取**修复特征**（新增的变量、函数、校验语句）；
2. 逐分支读取同一文件（`raw/<branch>/<path>`）；
3. 检查特征是否存在；
4. 记录三态：`present` / `absent` / `file_missing`。

仓库内脚本 `bulletin-hunting/scripts/check-fix-presence.mjs` 已实现这三态检测：

```bash
node bulletin-hunting/scripts/check-fix-presence.mjs \
  --repo <org>/<repo> --path <file> --marker <fix feature> \
  --branches <branch1>,<branch2>
```

它把 `absent` 汇总到 `needs_verification`，**不会**替你下「存在漏洞」的结论。

### 3.3 判定边界

| 结论 | 允许的表述 | 不允许的表述 |
|------|------------|--------------|
| 特征存在 | 「该分支该文件包含修复特征」 | 「该分支已修复全部同族问题」 |
| 特征缺失 | 「该分支该文件未见修复特征，需进一步验证可达性」 | 「该分支存在漏洞」 |
| 文件不存在 | 「该分支无此文件，需确认代码组织差异」 | 「该分支未修复」 |

**未见修复特征 ≠ 可利用漏洞**。它只是把「值得验证的分支」缩小到一个点。

### 3.4 常见误判

| 误判 | 原因 | 纠正 |
|------|------|------|
| 用 `master` 代表所有分支 | 各维护分支独立 | 逐分支读 |
| 用「文件相同」代替「逻辑相同」 | 同名文件可能已重构 | 比对修复特征，不比对文件哈希 |
| 把 cherry-pick 当成已同步 | 可能只 pick 了一部分 | 看目标分支实际内容 |
| 忽略「修复被回退」 | 后续 commit 可能 revert | 看分支最新状态，不看单个 commit |

## 4. 版本窗口与分支的对应

维护分支与产品版本**不是一对一**，映射需要显式记录：

| 分支（示例） | 对应产品线（示例） | 依据 |
|--------------|--------------------|------|
| `OpenHarmony-5.0.3-Release` | OpenHarmony 5.0.3 | 公告「受影响的版本」列 |
| `OpenHarmony-6.0-Release` | OpenHarmony 6.0 | 分支名 |
| `master` | 开发主线 | 非发布版本，不能当「最新公开版本」 |

规则：

- `master` **不等于**最新公开版本（`vuln-definitions-oh` 的 Gate V 明确要求最新公开版本）；
- 分支 → 版本映射必须来自公告或仓内发布说明，不能靠分支名猜产品版本号；
- 映射不确定时，写「映射未确认」，不要硬填。

## 5. 产物

`evidence/branch-check.md`：

```yaml
fix_ref: "<repo>@<sha> / PR <id>"
fix_feature: "新增 g_startReqListLock 并在请求链表读写处加锁"
branches:
  - branch: OpenHarmony-5.0.3-Release
    path: <file>
    state: present
  - branch: OpenHarmony-6.0-Release
    path: <file>
    state: present
  - branch: master
    path: <file>
    state: absent
conclusion: "master 未见该锁，需验证该路径在 master 的并发模型下是否仍成立"
```

`conclusion` 必须是**待验证**语气，不能直接写成漏洞结论。
