# 补丁差分反推与同族搜索

## 1. 为什么用差分而不是复现

已公开 CVE 的修复已经发布，复现它只证明「补丁前有洞」，对当前版本无价值。真正的收益在：

- **同模式未修点**：修复只改了一个调用点，同模块其他调用点仍缺同样校验；
- **同族实现**：同一缺陷模式在不同仓/不同语言里的复制品；
- **分支未同步**：修复只落在一条维护分支。

因此流程固定为：**读修复 → 提炼模式 → 找同族 → 验证**。

## 2. 获取 diff

按可用性排序：

| 方式 | 形态 | 说明 |
|------|------|------|
| PR 的 `.diff` | `https://host/<org>/<repo>/pulls/<id>.diff` | 最直接，实测可用 |
| compare | `https://host/api/v5/repos/<org>/<repo>/compare/<base>...<head>` | 跨分支差异，返回 commits/files |
| commit diff | `<repo>/commit/<sha>.diff` | 单提交 |
| 原始文件 | `<repo>/raw/<branch>/<path>` | 用于分支比对 |

注意：

- PR 元数据（标题、base 分支、合并时间）用 API 取，**不要**从页面文本猜；
- `files` / `changed_files` 字段可能为空，此时以 `.diff` 内容为准；
- diff 可能被截断（大 PR），必要时按文件分别取。

## 3. 从 diff 提炼缺陷模式

对每处改动，回答四个问题，写成结构化记录：

| 问题 | 记录 |
|------|------|
| 改了什么约束？ | 新增/收紧的校验、锁、边界、生命周期 |
| 原来为什么缺失？ | 漏判、错判、默认值、并发窗口、错误路径未回滚 |
| 触发条件是什么？ | 输入形态、调用顺序、并发、错误注入 |
| 影响是什么？ | 越界/越权/信息泄露/崩溃/状态错乱 |

### 3.1 常见缺陷模式清单

这些是公告机理在代码里的典型落点，用于**定位**，不是用于下结论：

| 模式 | diff 特征 | 同族搜索方向 |
|------|-----------|--------------|
| 缺长度校验 | 新增 `len` 比较、`size` 上限 | 同文件其他 `memcpy` / `strcpy` / 解析循环 |
| 缺返回值检查 | 新增 `if (ret != OK) goto err` | 同模块其他被忽略的返回值 |
| 缺锁 | 新增 mutex / 临界区 | 同结构体的其他读写点 |
| 生命周期断点 | 新增引用计数、延迟释放、置空 | 同对象其他释放路径、错误分支 |
| 边界计算错误 | 改 `+`/`-`/`*`、改 `sizeof` | 同族算术、同一宏的其他使用 |
| 类型混淆 | 新增类型检查 / 强转修正 | 同一 union / 多态分发的其他分支 |
| 反序列化不匹配 | 改 Parcel 读写顺序或类型 | 同接口的其他读写点 |
| 权限校验缺失 | 新增 caller/uid/token 校验 | 同 SA 的其他方法 |
| 路径校验缺失 | 新增规范化、前缀校验 | 同模块其他路径拼接 |
| 错误路径未清理 | 新增 `goto` 清理、回滚 | 同函数其他 `return` |

### 3.2 记录格式

```yaml
pattern_id: P-001
source_cve: CVE-XXXX-XXXXX          # 仅作内部索引，不进公开产物
fix_ref: "<repo>@<sha> / PR <id>"
changed_files:
  - path: <file>
    hunk: "<函数名>"
constraint_added: "对入参长度做上界检查"
root_cause: "解析循环按外部长度推进，未与缓冲区容量比较"
trigger_shape: "长度字段 > 实际缓冲区"
family_search:
  - "<同文件其他解析函数>"
  - "<同模块同类 API>"
status: hypothesis | verified | rejected
```

## 4. 同族搜索

### 4.1 搜索维度

按**由近到远**顺序，命中越近越值得投入：

1. 同函数其他分支；
2. 同文件同类调用；
3. 同模块同 API 的其他使用点；
4. 同仓相似模块；
5. 同族仓（如多个 `kernel_*`、多个 `*_framework`）；
6. 跨分支同一文件。

### 4.2 判定「可能同样缺失」

一个同族点要成为**可检验假设**，必须同时满足：

- 输入来源同类（外部可控、同信任级）；
- 缺失的约束确实不在该路径上（读过代码，不是猜）；
- 该路径在默认配置下可达；
- 有可观测的失败信号（崩溃、越界、越权结果、日志）。

缺任一条 → 记为「观察」，不进入候选。

### 4.3 优先级

同族点多时，按以下排序，不要平铺：

1. 默认配置可达 + 远程/近场入口；
2. 与修复点**同一数据结构**；
3. 代码更近（同文件 > 同模块 > 同仓）；
4. 历史上有同类公告的组件。

## 5. 常见误判

| 误判 | 表现 | 纠正 |
|------|------|------|
| 把「改了一行」当成完整根因 | 只看到加了个 `if` | 追问约束、触发、影响三件事 |
| 把加固/重构当漏洞修复 | diff 只是重命名或格式化 | 无约束变化 → 不是缺陷修复 |
| 同族点未读代码就断言 | 「这里看起来也缺」 | 必须读到该路径确实无校验 |
| 忽略调用方已有校验 | 下层缺校验但上层拦住 | 追到入口，确认可达 |
| 把测试用例改动当修复 | diff 只改 `*_test` | 测试改动不是安全修复 |
| 跨仓同名当同族 | 名字像但实现不同 | 以数据结构和调用约定判定 |

## 6. 与公告的衔接

- 公告给**机理**（越界写、UAF、权限绕过…），diff 给**落点**；
- 两者对齐后，才能说「该公告的修复模式是 X」；
- 若 diff 与公告机理不一致（如公告写 UAF，diff 只加日志），**以 diff 为准**，并记录不一致；
- 不一致本身是线索：可能是公告措辞泛化，或修复不完整。

## 7. 输出

`candidates.md` 每条至少包含：

- 假设（一句话）；
- 依据（diff 片段 + 同族点位置）；
- 可达性判断（默认配置、攻击者模型）；
- 验证方法（如何证伪）；
- 当前状态（hypothesis / verified / rejected）；
- **不写 severity**。
